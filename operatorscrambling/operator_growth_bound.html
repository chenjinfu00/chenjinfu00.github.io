Operator Growth Diagnostics

The same Heisenberg-picture Pauli algebra as the Operator Spreading Lab, run on an unbounded integer lattice to inspect finite-order Krylov/Lanczos coefficients without periodic wraparound. Finite-order differences are diagnostics, not certified Lyapunov bounds.

Set up the model

Compare presets only with the same seed, fixed window and step count. Early coefficients and stored-string counts are finite-order diagnostics; they do not by themselves classify a model as chaotic or integrable.

This is the Hamiltonian summed only inside a finite window. Its boundary participates from the first commutator, so it is not a nontrivial exactly conserved q=0 mode. Keep K fixed when comparing runs; two-dimensional windows become expensive quickly.

The seed sits at the origin of an infinite integer lattice — there is no boundary and no size to choose. Every offset below (\delta x, \delta y) is relative, so the same terms describe a chain (all \delta y=0) or a 2D lattice equally well.

Cost grows roughly ×3 per step (each step's reachable operator count is what the readout below calls reachable strings): steps 1–9 are instant, 10–12 take seconds, 13–15 can take tens of seconds to a minute or more. The chart updates after every step, so you can watch it grow and stop at any time.

Readout

Lanczos coefficient growth

|A_{n+1})=L|O_n)+b_n|O_{n-1}),\quad b_{n+1}=\lVert A_{n+1}\rVert,\quad |O_{n+1})=|A_{n+1})/b_{n+1}

L=i[H,\cdot\,] is the same real, antisymmetric generator as the Operator Spreading Lab's M, so the diagonal Lanczos term is exactly zero and only the off-diagonal b_n survive. Three views of the same run follow: b_n itself, adjacent finite-order differences, and the number of stored Pauli strings on a logarithmic scale. These views help diagnose a finite computation, but do not by themselves establish an asymptotic slope, a Lyapunov bound, or a chaos/integrability classification.

How this is different from the finite-lattice engines

The Operator Spreading Lab's two engines both need a lattice size: the exact operator-space engine because its sector is built from a fixed-length Pauli string, the state-vector engine because its Hilbert space is 2^N-dimensional. Both therefore either sit on a periodic torus (with a real wraparound artifact — see that page's own findings on small periodic lattices inflating the apparent butterfly velocity) or an open patch with boundary effects.

This page represents a Pauli string as a set of (x,y,\text{letter}) triples on \mathbb{Z}^2 instead of a bit-string of fixed length. There is consequently no lattice size to choose, no periodic wraparound, and no finite-N cutoff other than how many Lanczos steps are computed. Arithmetic is double precision with explicit numerical breakdown and resource checks; it is not an exact symbolic calculation.

Starting from the seed O_0=W_{(0,0)}, the three-term recursion above builds an orthonormal Krylov basis. Built-in correctness check: when the only term anticommuting with a Z seed is a single-site X field of strength h_x, b_1=2h_x exactly — the default preset is exactly the model this was checked against before publishing, and the readout below will show b_1=2.100 the first time you run it.

Interpret finite-order data conservatively. Adjacent differences of a short b_n sequence are not proven monotone bounds on the asymptotic coefficient. This page therefore reports diagnostics only and does not display a numerical Lyapunov bound.

Where this fits

This is one of three routes past the Operator Spreading Lab's 9-site operator-space ceiling documented there: larger periodic lattices (state-vector typicality, built into that page as its second engine, up to 16 sites), DTWA (a classical approximation, Python-only, which that page's own testing found measurably inflates butterfly velocity on small periodic lattices), and this lattice-size-independent coefficient diagnostic. Unlike the other two, this route answers a different question — finite-order Krylov growth, not a light-cone C_r(t) or a butterfly velocity — which is why it lives on its own page rather than as a third tab on the same one.

The same validated Python script behind this page's numbers (otoc16/krylov_infinite.py) is part of the delivered operatorspreading package, together with the DTWA script and the state-vector production scripts. The repaired page and Python implementation agree through the validated first eight coefficients; historical outputs with the old recurrence are retained but not treated as an oracle.
